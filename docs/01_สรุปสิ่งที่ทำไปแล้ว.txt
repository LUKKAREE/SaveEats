ส่วนที่ 2 : ทำไมเปลี่ยนมาใช้ TypeScript
================================================================================

แผนงานเดิมเลือก JavaScript แล้วบอกว่าต้องชดเชย 2 อย่าง (กฎข้อ 5)
      1. เขียน JSDoc กำกับทุก Model
      2. ตั้งชื่อ field ให้ตรงกันเป๊ะทั้ง Database <-> Backend <-> Mobile

ทั้งสองข้ออาศัย "ความจำและวินัยของคน" ซึ่งพลาดได้ง่ายมากเวลาทำงาน 3 คน

TypeScript ทำให้เรื่องนี้เป็นอัตโนมัติ
      พิมพ์ชื่อ field ผิด    -> ขึ้นเส้นแดงทันทีตอนพิมพ์
      ลืมเช็คค่าที่เป็น null -> ฟ้องทันที
      ส่ง parameter ไม่ครบ   -> ฟ้องทันที
      แก้ชื่อคอลัมน์ใน DB    -> ไล่ชี้ให้เองว่าต้องตามไปแก้ที่ไหนบ้าง

*** รายละเอียดทั้งหมดอยู่ในไฟล์ 05_TypeScript-ฉบับเริ่มต้น.txt ***
*** ถ้าไม่เคยเขียน TypeScript ให้อ่านไฟล์นั้นก่อนเริ่มงาน ***

หัวใจของการเปลี่ยนครั้งนี้คือโฟลเดอร์ shared/
------------------------------------------------
      shared/src/entities.ts  ประกาศหน้าตาข้อมูลทุกตารางไว้ที่เดียว
                              ทั้ง backend และ mobile ใช้ตัวเดียวกัน

      เดิม : ประกาศ 2 ที่ (backend/src/models + mobile/src/models) แล้วต้องดูแลให้ตรงกันเอง
      ตอนนี้ : ประกาศที่เดียว ถ้าไม่ตรง TypeScript ฟ้องทันที

[ข้อ 2] รายละเอียดของ Filter                   -> ทำให้แล้วบางส่วน
-----------------------------------------------------------------
  ตัวกรองทั้งหมดประกาศเป็นชนิด FeedQuery ไว้ที่ shared/src/dto.ts
  Backend รองรับแล้วที่ GET /api/posts
      search      ค้นหาชื่ออาหารหรือชื่อร้าน

[ข้อ 3] กติกาของ Behavior Score                -> ตั้งค่าเริ่มต้นให้แล้ว
-----------------------------------------------------------------
  *** ตัวเลขพวกนี้ตั้งไว้ให้ก่อน ทีมปรับได้ตามต้องการ ***
  แก้ที่ไฟล์เดียว : backend/src/services/behaviorScoreService.ts ตรงตัวแปร RULES

      เริ่มต้น                        100 คะแนน (สูงสุด 100 ต่ำสุด 0)
      ร้านยกเลิกการจองของลูกค้า        -5
      ลูกค้ามาถึงแล้วไม่มีของให้       -10
      ได้รีวิว 1-2 ดาว                 -2
      ส่งมอบอาหารสำเร็จ 1 ครั้ง        +1
      ได้รีวิว 5 ดาว                   +1

      คะแนน 70-100  -> good       ขายได้ปกติ
      คะแนน 40-69   -> warning    ขายได้ แต่ Admin เห็นเป็นสีเหลือง
      คะแนน 0-39    -> suspended  ระบบระงับร้านอัตโนมัติ Admin ต้องปลดเอง

  เพิ่มเติมจากแผนเดิม : สร้างตาราง behavior_logs ไว้ด้วย
  เก็บประวัติทุกครั้งที่คะแนนเปลี่ยน จะได้ตรวจย้อนหลังได้ว่าถูกหักเพราะอะไร

[ข้อ 4] เงื่อนไขการแจ้งเตือน                   -> ทำแบบเก็บลง DB
-----------------------------------------------------------------
  ตัดสินใจ : เก็บลงฐานข้อมูลแล้วให้แอปดึงไปแสดง ยังไม่ทำ Push Notification จริง
  เหตุผล : Push จริงต้องตั้งค่า Expo Push Service เพิ่ม ซึ่งใช้เวลาและซับซ้อน

  ตอนนี้ระบบยิงแจ้งเตือนเมื่อ
      ลูกค้าจองสำเร็จ                    -> แจ้งลูกค้า
      มีคนจองอาหารของร้าน                -> แจ้งร้าน
      ร้านยืนยันรับอาหารแล้ว              -> แจ้งลูกค้า (ชวนให้รีวิว)
      ร้านยกเลิกการจอง                   -> แจ้งลูกค้า
      การจองหมดอายุ                      -> แจ้งลูกค้า
      Admin อนุมัติ / ไม่อนุมัติร้าน       -> แจ้งร้าน
      ร้านถูกระงับเพราะคะแนนต่ำ           -> แจ้งร้าน

  ข้อความทั้งหมดอยู่ที่ TEMPLATES ใน backend/src/services/notificationService.ts
  ถ้าจะทำ Push จริง แก้ที่เดียวคือฟังก์ชัน notify() ในไฟล์เดียวกัน

[ข้อ 5] วิธีสมัครของ Seller                    -> สมัครเองในแอป + รออนุมัติ
-----------------------------------------------------------------
  ร้านสมัครเองในแอปได้เลย ระบบสร้างร้านให้ทันทีโดยตั้งสถานะเป็น pending
  Admin เข้าหน้า /stores/pending แล้วกดอนุมัติหรือไม่อนุมัติ
  ถ้าไม่อนุมัติ Admin ต้องกรอกเหตุผล ซึ่งร้านจะเห็นในแอป

  ร้านที่ยัง pending จะโพสต์ขายไม่ได้ (Backend บล็อกไว้ที่ requireOwnStore)

  *** ป้องกัน 3 ชั้นไม่ให้สมัครเป็น admin ผ่าน API ***
      ชั้น 1  ชนิด RegisterRequest ไม่ยอมรับค่า 'admin' (TypeScript ฟ้องตั้งแต่เขียนโค้ด)
      ชั้น 2  authValidator ปฏิเสธที่ระดับ route
      ชั้น 3  authService เช็คซ้ำอีกที เผื่อมีคนยิง API ตรงเข้ามา

   ส่วน backend/src/models/ ยังอยู่เหมือนเดิม เพราะเป็นที่เก็บโค้ด SQL

4. Backend ไม่ต้อง build เป็น JavaScript ก่อนรัน
   ใช้ tsx รันไฟล์ .ts ตรง ๆ ทั้งตอน dev และตอนใช้งาน
   ทำให้ขั้นตอนของทีมไม่ยุ่งยากขึ้นเลยแม้เปลี่ยนภาษา

5. เพิ่ม npm run typecheck ทั้ง 3 โฟลเดอร์
   รันก่อน commit ทุกครั้ง จะได้รู้ว่ามีอะไรพังไหมก่อนส่งงานให้เพื่อน

6. เพิ่ม backend/tests/selfTest.ts (npm test)
   ทดสอบ Logic 21 ข้อโดยจำลองฐานข้อมูล ไม่ต้องเปิด XAMPP

--- เรื่องฐานข้อมูล ---

7. เพิ่มตาราง categories
   เหตุผล : ข้อค้าง 7 บอกให้มีหมวดหมู่ แต่แผนเดิมไม่มีตารางรองรับ

8. เพิ่มตาราง behavior_logs
   เหตุผล : ถ้ามีแค่ behavior_scores จะเห็นแค่คะแนนปัจจุบัน
            Admin ต้องดูย้อนหลังได้ว่าถูกหักเพราะอะไร ตอนไหน

9. ย้าย discount_price / quantity / pickup_start / pickup_end จาก foods ไป posts
   เหตุผล : ค่าพวกนี้เปลี่ยนทุกรอบที่โพสต์ ส่วน foods คือเมนูตั้งต้นที่ไม่ค่อยเปลี่ยน

10. reservations เพิ่มคอลัมน์ post_id, unit_price, total_price
    post_id ทำให้รู้ว่าจองมาจากโพสต์ไหน เวลายกเลิกจะได้คืนของถูกโพสต์
    unit_price ล็อกราคา ณ ตอนจอง ถ้าร้านแก้ราคาทีหลังลูกค้าจะไม่โดนคิดเพิ่ม

11. เปลี่ยนชื่อ qr_code เป็น qr_token
    ชื่อเดิมชวนเข้าใจผิดว่าเก็บรูป QR จริง ๆ เก็บแค่ข้อความลับที่เอาไปวาด QR

--- เรื่องเครื่องมือ ---

12. ใช้ bcryptjs แทน bcrypt
    bcrypt ตัวเดิมต้อง compile ตอนติดตั้ง บน Windows มักติดตั้งไม่ผ่าน
    bcryptjs เป็น JavaScript ล้วน ติดตั้งได้ทุกเครื่อง ใช้งานเหมือนกัน

13. ตั้ง decimalNumbers: true ที่ mysql2
    ถ้าไม่ตั้ง คอลัมน์ DECIMAL (ราคา) จะกลับมาเป็นข้อความ ไม่ใช่ตัวเลข
    ซึ่งทำให้คำนวณผิดโดยไม่รู้ตัว

14. ไม่ใช้ LIMIT ? OFFSET ? แบบ prepared statement
    MariaDB ที่มากับ XAMPP มักตอบ error "Incorrect arguments to mysqld_stmt_execute"
    เปลี่ยนไปใช้ฟังก์ชัน paginate() ที่บังคับให้เป็นจำนวนเต็มแทน (ปลอดภัยเท่ากัน)

จุดที่ป้องกันปัญหาไว้เป็นพิเศษ
------------------------------
  1. คน 2 คนจองพร้อมกันแล้วของติดลบ
     แก้ด้วย : transaction + เงื่อนไข quantity_left >= ? ในตัว UPDATE เอง
     ดูที่ postModel.decreaseQuantity()

  2. QR ปลอมและการใช้ QR ซ้ำ
     แก้ด้วย : qr_token สุ่ม 32 ตัว + ตรวจที่ Backend ทุกครั้ง
               + เช็คว่าเป็นการจองของร้านนี้จริงไหม + เช็คว่าถูกใช้ไปแล้วหรือยัง
     ดูที่ reservationService.verify()

  3. รหัส 4 หลักซ้ำกันระหว่างร้าน
     แก้ด้วย : ค้นหาโดยระบุ store_id ด้วยเสมอ

  4. ร้านสแกน QR ของร้านอื่น
     แก้ด้วย : เช็ค reservation.store_id เทียบกับร้านของคนที่สแกน

  5. ลูกค้ารีวิวโดยที่ยังไม่ได้ไปรับของ
     แก้ด้วย : บังคับว่า status ต้องเป็น completed เท่านั้น

  6. password หลุดออกไปกับ response
     แก้ด้วย : ฟังก์ชัน toPublicUser() คืนชนิด PublicUser ซึ่งไม่มี field password
               ถ้าเผลอเขียนโค้ดที่ทำให้หลุด TypeScript จะฟ้องทันที

--------------------------------------------

        { "success": true, "message": "...", "data": [...],

    ล้มเหลว        ApiErrorResponse
        { "success": false, "message": "ข้อความภาษาไทย",
          "details": [ { "field": "email", "message": "..." } ] }

ส่วนที่ 11 : Flow การจองอาหาร - ทำงานจริงแล้ว
================================================================================

  1. Customer เลือกอาหารจาก Feed หรือ Map
            |
            v
  2. กดปุ่ม "จองอาหาร" -> POST /api/reservations
            |
            v
  3. authMiddleware ตรวจ Token           <- ไม่ผ่าน = 401
            |
            v
  4. roleMiddleware ตรวจว่าเป็น customer  <- ไม่ผ่าน = 403
            |
            v
  5. reservationValidator ตรวจข้อมูล      <- ไม่ผ่าน = 400
            |
            v
  6. reservationService.create() ตรวจ 5 อย่าง
         - โพสต์มีอยู่จริงไหม
         - ร้านยัง approved อยู่ไหม
         - โพสต์ยัง active ไหม
         - ยังไม่เลยเวลารับใช่ไหม
         - จำนวนไม่เกินที่กำหนดต่อคนใช่ไหม
            |
            v
  7. เริ่ม TRANSACTION
         7.1 ตัดจำนวน quantity_left (มีเงื่อนไข >= ในตัว UPDATE กันติดลบ)
             ถ้าตัดไม่ได้ = ของหมดพอดี -> rollback -> ตอบ 409
         7.2 สร้างแถวใน reservations พร้อม qr_token และรหัส 4 หลัก
     จบ TRANSACTION
            |
            v
  8. สร้างการแจ้งเตือนให้ทั้งลูกค้าและร้าน
            |
            v
  9. ส่งข้อมูลกลับเป็นชนิด ReservationDetail ซึ่งมี qr_payload ติดมาให้แล้ว
            |
            v
 10. แอปวาด QR จาก reservation.qr_payload ด้วย react-native-qrcode-svg
     และแสดงรหัส 4 หลักตัวใหญ่ไว้ข้าง ๆ
            |
            v
 11. ลูกค้าเดินทางไปที่ร้าน
            |
            v
 12. ร้านสแกน QR (หรือกรอกรหัส 4 หลักถ้าสแกนไม่ได้)
            |
            v
 13. POST /api/reservations/verify  { qrPayload } หรือ { code }
     *** ห้ามให้แอปตัดสินเองเด็ดขาด ***
            |
            v
 14. reservationService.verify() ตรวจ 5 ด่าน
         - แกะ token จาก payload ได้ไหม
         - เจอการจองนี้ในระบบไหม
         - เป็นการจองของร้านนี้จริงไหม     <- กันร้านอื่นสแกนตัดของ
         - ถูกใช้ไปแล้วหรือยัง             <- กันใช้ QR ซ้ำ
         - หมดอายุหรือยัง
            |
            v
 15. เปลี่ยนสถานะเป็น completed + บวกคะแนนความประพฤติร้าน +1
     + แจ้งเตือนลูกค้าให้มารีวิว
            |
            v
 16. ลูกค้าจ่ายเงินสด รับอาหาร แล้วเขียนรีวิวได้
